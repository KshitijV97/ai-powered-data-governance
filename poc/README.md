# Borealis Bank PIPEDA governance POC (OpenMetadata 2.0.5)

A small, reproducible proof of concept for the GNG/ELG 5301 team project
*AI-powered data governance with OpenMetadata for PIPEDA compliance*.

**Borealis Bank of Canada is fictional. Every row of data is synthetic**
(generated by `toolbox/poc/generate_data.py`): names come from generic lists,
e-mails use the reserved `example.*` domains, phone numbers use the fictional
555-01XX exchange, IPs use the RFC 5737 documentation range, and SINs and card
numbers are random Luhn-valid strings that belong to no one. No human-participant
data is collected, as the course guidelines require.

Detailed documentation (architecture, data model, governance model, results, operations) is in [`../docs/`](../docs/README.md).

## What it demonstrates

| PIPEDA principle | What the POC does in OpenMetadata | Evidence file |
|---|---|---|
| 4.1 Accountability | Privacy Office team, Chief Privacy Officer persona owns the PIPEDA classification and glossary; every table has an owner and domain | `results/pipeda_compliance_summary.md` §3 |
| 4.2 Identifying purposes | `PIPEDAPurpose.*` tags on each table; purpose stated in a data contract | §3, data contract |
| 4.3 Consent | Data-quality tests on consent; a catalogue-generated consent row filter for marketing | §2, §5 |
| 4.4 Limiting collection | AI classification surfaces stored CVVs and legacy SINs | §1, §2 |
| 4.5 Retention | `retentionPeriod` on tables + retention tests | §2, §3 |
| 4.6 Accuracy | Format / uniqueness tests | §2 |
| 4.7 Safeguards | Tag-based OpenMetadata policies; masked views + grants generated from catalogue tags | §4, §5 |
| 4.8 Openness | PIPEDA business glossary approved through the glossary approval workflow | `results/workflow_audit.json` |
| 4.9 Individual access | Column-level lineage OLTP → warehouse; AI-assistant (MCP) lineage query | `results/mcp_transcript.json` |
| 4.10 Challenging compliance | Recognizer-feedback workflow (steward reports, CPO approves) | `results/workflow_audit.json` |

**AI features used:** OpenMetadata auto-classification (Microsoft Presidio
recognizers + spaCy NER), custom Canadian recognizers (SIN, postal code, Ontario
licence, passport), the recognizer-feedback governance workflow, and the built-in
MCP server that lets AI assistants (Claude, Cursor, …) query the catalogue.

## Architecture

```
            ┌──────────────── Docker network ───────────────────────────────┐
            │  OpenMetadata 2.0.5 server ── Postgres (metadata) ── Elastic  │
            │        ▲  REST / MCP                                          │
 toolbox ───┤        │                                                      │
 (Python)   │  om-cli (openmetadata/ingestion image: ingest, classify,     │
            │          profile, test)  ──reads──►  bank-db (Postgres 16)   │
            │                                       ├─ core_banking (OLTP) │
            │                                       └─ bank_dw (OLAP star) │
            └───────────────────────────────────────────────────────────────┘
```

* `openmetadata/docker-compose-openmetadata-postgres.yml` – the **official,
  unmodified** OpenMetadata 2.0.5 compose file.
* `docker-compose.poc.yml` – overlay: the bank database, the toolbox, a one-off 
  ingestion runner, and memory limits so everything fits a 4 GB Docker VM.
  The Airflow ingestion server is optional (`--profile airflow`).

## Run it

Requirements: Docker Desktop with ≥ 4 GB memory (6 GB is more comfortable), ~8 GB disk.

```bash
./scripts/run_poc.sh
```

The full run takes about 15–20 minutes. Then open <http://localhost:8585>. The quickstart admin is
`admin@open-metadata.org` / `admin`; the persona accounts (`priya.cpo`,
`dan.steward`, `maya.marketing`, `femi.aml`, `eli.engineer` @borealis.example)
use the local test password in `toolbox/poc/bootstrap_governance.py`.

Resume from a step with `./scripts/run_poc.sh --from 8`. Wipe everything with:

```bash
./scripts/reset.sh
```

## Steps (scripts/run_poc.sh)

1. Start OpenMetadata + bank DB
2. Generate synthetic OLTP data; ETL into the star-schema warehouse (with a planted consent bug)
3. Teams, personas, roles, domains, purpose tags, PIPEDA glossary
4. Metadata ingestion for both databases
5. **Baseline** auto-classification with the out-of-the-box `PII` recognizers → scored against ground truth
6. **Canada-tuned** `PIPEDA` classification (custom recognizers) → scored
7. Human-in-the-loop: CPO approves the glossary; steward reports false positives; CPO approves → re-run → scored
8. Owners, domains, purposes, retention, sensitivity roll-up, lineage through a registered ETL pipeline
9. Profiler + PIPEDA data-quality tests (failures here are expected findings)
10. Data products, glossary links, data contract on the marketing mart
11. Catalogue access-control tests per persona + warehouse masked views generated from tags
12. AI-assistant questions through the OpenMetadata MCP server
13. `results/pipeda_compliance_summary.md`

## Connect an AI assistant (optional)

OpenMetadata's MCP endpoint is `http://localhost:8585/mcp`. Generate a personal
access token for a **least-privilege** user (not admin: the MCP server exposes
write tools such as `patch_entity`), then follow the OpenMetadata guide for
Claude Desktop / Claude Code. `toolbox/poc/mcp_demo.py` shows the calls.

## Findings worth knowing (details in the report)

* In OpenMetadata 2.0.5 OSS, `metadata classify` hard-codes the `PII`
  classification (`metadata/workflow/classification.py`), so recognizers on
  other classifications are ignored. `om-ext/classify_with.py` reuses the
  official workflow class with a different classification filter.
* None of the built-in recognizers targets Canadian identifiers; the baseline
  caught SINs only because an *Australian TFN* and a *US ABA routing* pattern
  happened to match.
* The sample-data endpoint enforces `matchAnyTag()` policies on table-level
  tags only, so column sensitivity must be rolled up to the table.
* Custom (Python) recognizers are not implemented in the OSS engine, so SIN
  checksum (Luhn) validation is not possible; SIN detection is regex-based.
