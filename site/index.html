Can AI-assisted data governance make a Canadian bank PIPEDA-ready?

We built a fictional bank on synthetic data, governed it with the open-source catalogue OpenMetadata 2.0.5, and measured what its AI features get right, what they miss, and where people still have to step in.

The problem

Banks copy customer data from the systems that collect it into warehouses and marts for marketing, anti-money-laundering and analytics. Every copy is personal information under Canada's PIPEDA, yet most banks cannot say which columns hold it, why it is kept, who may read it, or when it must be deleted. AI-assisted development adds pipelines faster than people can review them.

Research question

How, and with what professional safeguards, can a Canadian bank use an open-source, AI-assisted metadata platform to put PIPEDA's ten fair information principles into practice across its operational (OLTP) and analytical (OLAP) data?

Why it matters

The Privacy Commissioner's investigation of the 2019 Desjardins breach, which affected about 9.7 million people, found failures of access control, data segregation and safeguards. These are the controls a metadata catalogue claims to support.

Approach

A structured literature review set the claims to test. A proof of concept then tested them end to end on Borealis Bank of Canada, a fictional bank with 1,500 synthetic customers. The whole pipeline runs with one command in Docker, so every number on this page can be reproduced.

  1. Build the bankCore-banking OLTP database, nightly ETL into a star-schema warehouse with marketing and AML marts. Realistic defects are planted on purpose.
  2. Catalogue itOpenMetadata ingests and profiles both databases and records column-level lineage from source to warehouse.
  3. Find personal information with AIPresidio and spaCy auto-classification, extended with Canadian recognizers for SINs, postal codes, account numbers, licences and passports.
  4. Keep people in chargeData stewards correct false positives through a feedback workflow; the Chief Privacy Officer approves glossary terms. Every decision is audited.
  5. Express PIPEDA as metadataOwners, domains, purposes, retention periods and sensitivity tags on every table, mapped to the ten principles.
  6. Test and enforceCompliance tests named after the principle they check, tag-based access policies, and masked warehouse views generated from the same tags.
  7. Ask an AI assistantAn agent answers privacy questions from the catalogue through OpenMetadata's Model Context Protocol (MCP) server.

What the numbers mean

The built-in recognizers missed account numbers, dates of birth, postal codes, identity-document numbers and a legacy SIN column. They matched SINs only through Australian and US number patterns.

Canada-specific recognizers found every personal-information column, but also tagged three city columns. One round of steward feedback removed those false positives and left an audit trail.

Accuracy is a property of the deployment, not the product. A perfect score on synthetic columns shows the method works here, not that it generalises to a real bank.

Catalogue policies stop at the catalogue

Tag-based policies blocked a marketing analyst from viewing sample data on high-risk tables (HTTP 403) and from removing a PIPEDA.HighRisk tag. All 7 catalogue checks behaved as expected.

But the same analyst could still query the warehouse directly with SQL. Closing that gap took a script that reads the catalogue's tags and generates masked views and grants. All 7 warehouse checks then behaved as expected.

A living inventory of personal information

All 14 tables carry an owner, a domain, a processing purpose and a retention period. Twelve carry a rolled-up sensitivity tag: 5 high-risk, 5 direct-identifier and 2 financial. The two consent tables hold no tagged personal-information columns.

Column-level lineage traces each customer field from the core-banking database through the ETL into the warehouse and marts.

An AI assistant can answer privacy questions, and change metadata

Through OpenMetadata's MCP server, an AI agent answered four PIPEDA questions using the catalogue alone. The server exposed 15 tools, including tools that create and modify metadata.

4.7 Which tables hold high-risk identifiers?

Searched by the PIPEDA.HighRisk tag and returned 6 tables.

Followed downstream lineage from core.customer into the warehouse and marts.

Returned the table's data-quality status, including the failing consent test.

Found the approved glossary definition.

Product limitations we found

These are behaviours of OpenMetadata 2.0.5 open source that we found while building the proof of concept, with the workaround used for each.

Classification

Custom classifications never run

The metadata classify command hard-codes the built-in PII classification. Workaround: a small subclass that runs custom recognizers.

Classification

No Canadian identifiers built in

No built-in recognizer targets SINs, postal codes, account numbers or licences. Workaround: custom PIPEDA recognizers.

Classification

No checksum validation

Custom Python recognizers are not available in open source, so there is no Luhn check on SINs. Workaround: regex, context words and column names.

Access control

Policies read table tags only

The sample-data endpoint evaluates tag conditions on table-level tags, while the permission debugger also counts column tags. Workaround: roll the most sensitive column tag up to the table.

Access control

Policies don't reach the database

Catalogue policies don't apply to SQL users. Workaround: generate warehouse views and grants from catalogue tags.

AI agents

MCP exposes write tools

An over-privileged agent could remove safeguarding tags. Workaround: least-privilege tokens and an organisation-wide tag-integrity policy.

Takeaways

An AI-assisted metadata platform can put PIPEDA into practice as a supervised control system, not an autonomous one.

Strong

Knowing and documenting

Inventory, purposes, glossary and lineage (principles 4.2, 4.4, 4.8, 4.9) map well onto catalogue metadata.

Useful but incomplete

Detecting violations

Tests detect consent, retention and accuracy problems (4.3, 4.5, 4.6). The fix still lives in pipelines and processes.

Weak without extra work

Protecting the data

Safeguards (4.7) protect the catalogue, not the database, unless tags are wired into enforcement.

Limits of this study: the bank and its data are synthetic, and results are not evidence of effectiveness in production banking or of regulatory compliance. This is a course project, not legal advice.

Reproduce it

The proof of concept runs end to end with one command. It needs Docker with about 4 GB of memory and takes 15 to 20 minutes. Using the same seed reproduces every number on this page.

git clone https://github.com/KshitijV97/ai-powered-data-governance.git
cd ai-powered-data-governance
poc/scripts/run_poc.sh

Stack: PostgreSQL 16, OpenMetadata 2.0.5, Microsoft Presidio and spaCy, Python, Docker Compose. Results are written to poc/results/.
